  - 詳細な表と条件は note の probe メモ(リポジトリ管理外)にあり、評価の本番結果は `doc/experiments/` に置く予定。

## 2026-09-30 — 準備の不公平の修正と測り直し

**きっかけと原因**
- デモ UI を動かしていて、同じ画像を2回目に判定した JSON 方式が、1回目よりずっと速いことに気づいた(G05・G06 で2回目が 566〜657 ms)。
- 9B で確かめた(作業中の確認。デモ用に起動していた改造版 llama-server・Qwen3.5 9B・長辺1024 に、classifier_demo の関数で G05(選択式の準備あり)と G06(準備なし)を2回ずつ送った手動計測。出力は会話の中だけでファイルには残していない): 選択式の準備(`--prime` の準備リクエスト)を送ったあとの JSON の判定は 1589 ms、準備なしの JSON は 1487 ms で、準備が JSON には効いていなかった。準備は選択式の system 文で送っていたため、JSON 方式の先頭(system 文が違う)には一致せず、キャッシュに載らなかった。つまり `--prime` 付きの実行(E9/E7/E7e、最終の取り直し F1〜F3、小型 S1〜S9)では、JSON の判定時間だけ画像の読み込みを含み、選択式・束ね質問は含まなかった。精度は影響を受けない。
- 「束ね質問は JSON の約2倍速」「1軸ずつは JSON と同程度」という当初の読みは、この不公平による見かけの差だった。

**修正(PR #20、merge 済み)**: `--prime` を方式ごとの準備にした(各方式が自分の質問形式で準備する。`run.json` の `prime_scope=per_mode`)。
