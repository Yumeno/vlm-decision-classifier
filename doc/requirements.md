# ローカルVLM選択式画像分類デモ — 要件定義書

- 文書版: 0.4（MVP理念に沿って評価出力・公開安全性確認を簡素化、E6を追加課題化）
- 作成日: 2026-09-23
- 対象: `自家製の画像分類アプリ(非公開)` の分類方式を独立して実演する公開リポジトリ
- 関連文書: `basic-design.md`、`implementation-experiment-plan.md`

## 1. 背景と目的

本プロジェクトの発想の起点は**Jev**と、Jevに着想を得て**DiffusionGemmaを構造化された分類・意思決定に使う実装を紹介したGoogle GemmaのX投稿**である。添付の投稿画像と、投稿から参照された[vLLMのPR #57250](https://github.com/vllm-project/vllm/pull/57250)を確認した。PRはmmastrac氏が作成し、2026-09-22にマージされた。そこから「選択肢への確率的な回答を、手元で動く画像分類にも応用できるか」という着想で元プロジェクトの実装・実験に進んだ。記事とREADMEにはこの順序を明記し、発想と独立実装、測定結果を分けて述べる。

既存プロジェクトの価値のうち、ローカルVLMによる選択式・複数軸の画像分類を抽出して、読者が自分のPCで試せる小さな公開デモとする。専用に新規生成するデモ・テスト画像データセットを同梱し、通常版Qwen3.5 9B GGUFとGemma 4 12Bの結果を再現可能な形で示す。Qwenの多質問処理で重要だったllama.cppの画像キャッシュ改造も独立した比較条件として記録する。元プロジェクトの画像、個人の画像ライブラリ、既存の正解セットは流用しない。

公開の主張は「logprobsによる画像分類の発明」ではない。選択肢の確率分布、軸ごとの質問、複数対象の確認、生成メタデータの確定的な照合、判定根拠の表示を一つの実行可能な例に統合した点を示す。研究的な新規性や他方式への優越性は、実験結果の範囲を超えて主張しない。

## 2. 対象読者と成功状態

- 読者: ローカル生成AIや画像整理に関心を持つ開発者。PythonとLM Studioの基本操作を想定する。
- 成功状態: READMEに従って標準Qwen3.5 9B GGUFまたはGemma 4 12Bの対応GGUFをロードし、同梱画像の単体分類と固定評価を実行できる。分類結果と根拠、再現条件、失敗例を見られる。
- 別用途: note記事の実証資料。記事はリポジトリの特定コミット・データセット版・実測結果に結び付ける。

## 3. スコープ

### 3.1 必須

1. 画像を少なくとも `image_type`、`art_style`、`subject`、`character` の独立軸で判定する。典型的なカテゴリの語彙と判定基準を公開YAMLで指定する。軸間は排他的にしない。
2. キャラ軸は自作キャラ「Alisa」（LoRAトリガー `fet_alisa_uniform`、Anima用LoRA `fet-alisa-uniform-anima-v4u`）、容姿が似た別の自作キャラ、`other_original` を含め、複数名の同時検出を扱う。公開前に作者が表示名、設定、外見基準を確認する。
3. PNGのA1111/Forge形式の `parameters` からLoRA指定・プロンプトタグを抽出し、taxonomyに列挙したAlisa用LoRA名の集合と厳密一致で照合する。ComfyUIはworkflow JSONのLoraLoader系ノードの`lora_name`からLoRA名だけを抽出する。JPEG/WebPは対応できる範囲を実装・テストで確定してREADMEに記載する。未対応形式はメタデータなしとして画像判定を続ける。
4. 画像からの容姿判定とメタデータ上のLoRA指定を別の証拠として保持し、両者が矛盾する場合も表示する。「LoRA名が記録されていた」を「実際にLoRAが適用された」の証明として扱わない。
5. 軸ごとに短い選択式質問を行い、回答ラベルの `logprobs` から候補間スコアを計算する。候補選択、多人数の追加yes/no、`none`/`other`、候補数上限、推論失敗時の扱いを明示する。
6. 1枚の実演と固定データセット全件の評価をCLIから実行できる。最低限、画像、最終タグ、証拠の由来、候補分布、実際の質問回数、所要時間をJSONに出力する。人向け表示はCLIのテーブルまたは軽量なローカル画面とする。
7. 専用画像を新規生成し、正解ラベル・生成条件・公開権限確認を記録する。元画像を生成・検収した後、メタデータ除去版などの派生ケースを作る。派生ケースは同一元画像グループとして集計する。
8. 通常版Qwen3.5 9B GGUFを主モデル、Gemma 4 12Bの対応GGUFをSFW比較モデルとする。量子化、mmproj、ランタイム版、GPUオフロード、解像度、起動引数を実験ごとに記録する。既存プロジェクトの無検閲派生版の測定結果はデモの測定値として転載しない。
9. Qwenの比較として、同じllama.cppコミットから作る未改造版と画像キャッシュ改造版を区別して動かす。パッチの対象コミット、差分、ビルド条件、適用・戻し方を文書化し、ベンチマーク結果に実行バイナリの識別子を残す。初版の通常分類には改造版を必須としない。
10. ソース、taxonomy、画像、正解、評価コード、再現手順、ライセンスと出典を公開リポジトリに用意する。モデル重みとLoRA本体は分類デモの実行要件に含めない。
11. **通常JSON分類を必須ベースライン**として実装する。画像と同じtaxonomyの全軸・候補・判定基準を提示し、通常のVLMに分類JSONを回答させる。選択式方式と同じケースで、正答率・所要時間・JSON形式不正・再試行・失敗を比較する。

### 3.2 任意・後続

- LM Studioに加えてllama-serverを選択可能にする。先に同じAPI契約を満たすか検証する。
- 単独質問に対し束ね質問を比較実験として追加する。初版の基準は単独質問。
- 説明文（要約）付きJSON生成との比較（実験E6）。元プロジェクトでは実施しているため追加課題として積むが、優先度は低く、初版MVPの完了条件に含めない。
- 結果確認用の小さなWeb画面。必要ならCLI出力と同じJSONを読む静的ビューとし、画像管理アプリへ拡張しない。
- 実行時の独自taxonomy差し替え。初版は同梱設定が完全に動くことを優先する。

### 3.3 対象外

元アプリの画像ライブラリ管理、DB移行、画像移動・複製、サムネイルキャッシュ、バックグラウンドジョブ、ONNX Tagger、カテゴリ自動育成とレビューUI、外部有料API、LoRA学習・配布、版権キャラの同定。これらを依存として持ち込まない。

## 4. データセット要件

### 4.1 構成

初回目標は**独立した元画像24枚程度**。確定枚数は生成可能性と外見の検収後に固定し、変更したらdataset versionを上げる。内訳は設計目標であり、生成しながら都合のよい画像だけ選んで試験結果を押し上げない。

| 群 | 独立元画像の目安 | 主な検証 |
|---|---:|---|
| 一般カテゴリ | 8 | 人物・風景・メカ・小物等、画風と画像種別 |
| AlisaのLoRAあり | 4 | メタデータと容姿の一致 |
| AlisaのLoRAなし | 3 | 容姿だけの同定 |
| 似た別の自作キャラ | 4 | 誤同定の抑制 |
| 二人以上 | 3 | キャラの再現率と余計な付与 |
| メタデータと画像の矛盾 | 2 | 不一致の表示と判断保留 |

指定数が不足した群は不足を公表し、後から埋めた結果を別版として扱う。メタデータ除去コピーは独立元画像数に数えない。明確な矛盾例は、生成記録と実際の画素を別々に管理して人工的に用意した評価ケースと明示する。

### 4.2 データ仕様

- `dataset/manifest.jsonl`: `case_id`、`source_image_id`、`image_path`、`split`、`scenario`、`generation_metadata`（公開可能なもの）、`expected`、`rights_confirmed`、`review_status`。元画像と派生例の関係を必ず持つ。
- `expected` は軸ごとの集合。画像を見た複数の人物を記録し、LoRA指定の有無は画像上の正解ラベルから分離する。
- 生成画像は作者本人が画素、キャラらしさ、重複、混入物、掲載可能性を目視検収する。生成プロンプトは公開前に個人情報・固有作品名を点検する。
- 権利確認できない画像を公開セットに含めない。モデルやLoRAの利用条件は生成・公開に用いたものを個別に確認し、使用条件とクレジットを記載する。
- 同一画像のサイズ違い、メタデータ除去版、同一シードの近似画像はグループ単位で分割し、評価上の独立性を偽らない。

## 5. 機能要件と受入条件

| ID | 要件 | 受入確認 |
|---|---|---|
| FR-01 | 二系統モデルのローカル接続 | health checkで接続、モデルID、vision・logprobsの可否を確認。不対応なら明示的に停止 |
| FR-02 | 選択式軸判定 | 同梱taxonomyから質問を作り、軸ごとの候補スコアと`none`を保存 |
| FR-03 | 複数キャラ | 同一画像で2名の正解を表現でき、必要な候補ごとに存在確認が走る |
| FR-04 | LoRA照合 | 大文字小文字・空白等の規定正規化後の名前の完全一致だけを採用。部分一致しない |
| FR-05 | 根拠の分離 | `metadata_lora`、`metadata_prompt`、`vision`を別記録。矛盾時にどちらかを消さない |
| FR-06 | 再現性 | 全入力・taxonomy版・モデルID・設定を結果とともに保存し、再実行コマンドをREADMEに記載 |
| FR-07 | 固定評価 | 軸別、キャラ別、複数人、矛盾群の結果と遅延を、ケース別CSVと集計Markdownで出す |
| FR-08 | 公開安全性 | リポジトリに元アプリ由来の個人画像、秘密情報、モデル重み、LoRA重みを含まないことを公開前チェックリストで確認する（自動検査スクリプトは作らない） |
| FR-09 | Qwen画像キャッシュ比較 | 同一コミット・同一モデル・同一画像・同一設定で未改造/改造を比較し、分類結果の差も記録 |
| FR-10 | GemmaのSFW評価 | SFW subsetの精度・失敗率・遅延をQwenと同じ尺度で測る。対応不可の群は適用範囲外と記す |
| FR-11 | JSON生成ベースライン | QwenとGemmaの各評価対象で、同じtaxonomyと画像を用い、通常JSON分類の精度・所要時間・形式不正・再試行を記録。選択式との比較表を出す |

## 6. 非機能要件

- Windows 11を第一検証環境、Linuxをコード上の可搬性対象とする。Pythonは3.11以上。WindowsのPowerShellでコピーできる起動例を用意する。
- 推論先は既定で `127.0.0.1` のみ。外部送信を要しない。任意の接続先を許す場合も利用者が明示したURLに限定し、秘密情報や画像の意図しない送信を防ぐ。
- 画像の読み込みはPNG/JPEG/WebPを対象とし、長辺1024px以下への推論用縮小を初期値とする。原画像は変更しない。実測に基づく768px比較は別条件として記録する。
- 1画像の失敗で全件が停止しない。各ケースにエラー種別を保存し、成功率の分母から都合よく除外しない。
- 画像/メタデータ内テキストは信頼できない入力。補助データを命令として扱わず、制御文字・過大な文字列を制限する。ローカル画面を設ける場合はエスケープして表示する。
- 推論条件、ライブラリ版、taxonomy、画像、しきい値を固定して比較する。性能の目標値は標準9B GGUFの実測後に設定し、既存派生モデルの数値で受入を決めない。

## 7. 公開の受入ゲート

1. 自作の固定データセットとmanifestが整い、公開権限が全件確認済み。
2. 標準9B GGUFで単体デモ・全件評価、Gemma 4 12BでSFW subset評価を第三者が手順通り再現できる。Qwenの改造比較は別の任意手順として再現できる。
3. 画像正解とメタデータ正解を分けて採点し、混同行列・ケース別の失敗・測定条件を提示する。
4. 比較主張は同じモデル・同じ画像・同じ基準で比較した範囲に限る。優位が出なければそれも報告する。
5. READMEとnote原稿で、スコアの解釈、LoRA記録の意味、データセットの規模、一般化の限界を明記する。
6. 通常JSON分類と選択式分類のケース別結果・速度を、同じモデルと画像に対する対応比較として提示する。JSONに要約を生成させる場合は出力トークン数の違いを明記し、分類のみの比較と区別する。

## 8. 要確認事項と暫定方針

| 論点 | 暫定方針 | 確定タイミング |
|---|---|---|
| 自作キャラの表示名と外見基準 | 仮称Alisa。作者が定義原文と公開範囲をレビュー | 画像生成前 |
| データセット生成モデルとLoRAの掲載条件 | 公開可能な組合せを作者が選び記録 | 画像生成前 |
| 通常版GGUFの量子化とmmproj | 推論が成立する組合せを固定しSHA256を記録 | 最初の接続検証 |
| Gemma GGUFの配布元と量子化 | Google公式モデルとの対応が確認できるGGUFを選び、画像入力とlogprobsを実測 | 最初の接続検証 |
| llama.cpp改造パッチ | 元プロジェクトの検証済み差分を起点に、固定コミットで再検証 | パッチ評価前 |
| Web画面の有無 | CLIを必須、画面は任意 | コア実装完了後 |
| 公開リポジトリ名とライセンス | 仮名を用い、公開前に作者が確定 | 公開前 |
