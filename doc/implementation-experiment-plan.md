# ローカルVLM選択式画像分類デモ — 実装・実験計画書

- 文書版: 0.5（MVP理念に沿って移植対応表・taxonomy検証・レポート形式を簡素化、E6/E7を追加課題化）
- 作成日: 2026-09-23
- 対応文書: `requirements.md`、`basic-design.md`

## 1. 実施方針

作業の中心は、専用画像セットを先に固定し、分類方式とモデル・実行環境の差を同じ入力で評価すること。すべてを一度に公開せず、公開可能なコード・画像・結果・記事原稿を揃え、再現試験を通してから公開する。公開リポジトリの新規作成とnote投稿は別の最終工程とする。本書は作業計画であり、コード・データセット・測定結果が既に完成したことを意味しない。

## 3. フェーズと実施順

### Phase 0: ソース・権利・実行環境の固定

1. 元リポジトリの `decision_provider.py`、`taxonomy_grow.py`、`metadata.py`、画像キャッシュパッチと関連テストを最新版の特定コミットで読む。移植した関数と元コミットは、移植したPRの説明に列挙する（別途の対応表は作らない）。READMEや作業記録の予定と、実際のmainにあるコードを区別する。
2. 別リポジトリへのコード移植に適用するライセンスを確認する。元リポジトリのライセンスが未設定なら、権利者本人として新規公開コードへのライセンス付与方針と既存コードの扱いを決める。外部依存のライセンスも列挙する。
3. Qwen公式モデル `Qwen/Qwen3.5-9B` と選定GGUFの対応、量子化、mmprojを確認。Gemma 4 12B itも同様に確認する。入手先、commit/revision、SHA256を記録する。
4. 記事のクレジット欄には、Jev、ユーザーが示したGoogle GemmaのX投稿、投稿が参照するmmastrac氏のvLLM PR #57250を順に載せる。開発者によるX原投稿は投稿画像中に短縮表示されているため、正確なURLを確認できた場合だけ追加する。関連するOpenJevのコードを元のX投稿そのものと取り違えない。

**退出条件:** 出典表、モデル候補表、公開画像生成に使うモデル・LoRAの利用条件を記録。

### Phase 1: データセット仕様・生成・検収

1. 正解付与規則を確定する。`subject`が2種類ある場合、キャラが写っていない場合、似た服装だけ一致する場合、二人絵で片方が小さい場合を明文化する。
2. 目標24元画像の**生成計画表を結果を見る前に保存**する。画像ID、群、狙う一般カテゴリ、キャラ構成、LoRA指定、メタデータ状態、乱数seed、生成モデル、画像比率を予定として列挙する。
3. 元プロジェクトの既存画像を使わず、作者が公開権を持つモデル・LoRA・素材の組合せで新規生成する。可能な限り同じ生成系で群間の比較を揃え、群の違いが画風の違いだけにならないようにする。
4. 失敗生成・不明瞭な人物・重複・権利不明は検収理由付きで除外する。追加生成が必要なら予定と実績を別列に記録し、都合の良い画像のみを後選びしたことが分かるようにする。
5. メタデータなしの対照ケースは確定済み元画像から複製して作る。LoRA名だけが偽の矛盾ケースは評価用に変更したメタデータだと明記し、実生成情報として扱わない。画像のSHA256と元画像グループを記録する。
6. 正解ラベルはモデル結果を見ずに付け、作者による目視検収を保存する。必要なら別の評価者による一致確認を追加する。データセット版を固定し、評価中に編集しない。

**退出条件:** manifestのスキーマ検証成功、参照画像全件存在、`rights_confirmed=true`、シナリオ別件数と派生関係が一致、画像の目視確認完了。

### Phase 2: 最小の分類コア

1. taxonomy YAMLの読み込み時に最低限のチェック（IDの重複、1質問の候補数上限）だけを行う。網羅的なバリデータは作らない。
2. PNG metadataからLoRA指定を抽出。ファイル拡張子ごとのサポート範囲を検証し、取得できない場合は `metadata_unavailable` とする。
3. `Choice`、`DecisionBackend`、`axis_decision`、`evidence_merge` を独立実装。候補ラベルの複数トークン化や欠損、返却順序の変動、圧倒的な`none`、yes/noの欠損をテストする。
4. QwenをLM Studioでprobeし、単体1枚のJSON出力まで通す。キャラ軸の複数判定を追加し、meta有無の対照ケースに対する説明が区別できることを確認。
5. まずCLIの単体分類と固定評価を完成させる。結果ビューは必要になれば出力JSONを読み込むだけの独立レイヤーとして追加する。
6. 同じtaxonomyの全軸・候補を提示して分類JSONを1回生成させるベースラインを実装する。分類項目のみのプロンプト、解析ルール、再試行上限を事前に固定し、同じmanifestで評価する。

**退出条件:** 単体実行と全件ループが再現し、少なくとも正常・メタデータなし・複数キャラ・入力不正・logprobs欠損の経路で期待した構造を出す。テストは数値集計やエラー処理を検証し、実モデルの答えを固定値として断定するテストは作らない。

### Phase 3: モデル・ランタイム検証

1. Qwen通常版9B GGUFでvision・選択文字・`top_logprobs`・thinking制御を検証する。想定が成り立たなければモデル/サーバーの組合せを変えて再試験し、変更理由を記録する。無検閲派生版の結果で代用しない。
2. Gemma 4 12B itのGGUFで同じprobeを実施し、SFW全ケースを回す。安全方針による拒否、先頭思考トークン、回答フォーマット不適合があれば失敗として件数化する。
3. 別モデルと同じ画素で比較する。モデルによる差と、LM Studio対llama-serverによる差が混ざらないよう、モデル間比較は同一サーバー条件を優先し、実現できない差は表に明記する。

**退出条件:** Qwenで全件評価が成立し、GemmaでSFW subsetの成功率と失敗例が記録される。Gemmaでキャラ軸が十分か、一般分類向けの役割が適切かを結果から判断する。

### Phase 4: llama.cpp画像キャッシュ改造の再現

1. 上流llama.cppのcommitを固定。元リポジトリの `docs/patches/llamacpp-mtmd-cache.patch` を起点に、対象行と適用後の差分を確認し、公開デモ内のパッチとして固定する。
2. 同じcommitから未改造版・改造版の `llama-server` を別のビルドディレクトリに生成。CUDA、CMake、コンパイラ、GPU、プロジェクタ、コンテキスト、GPUオフロード、スロット数を記録する。モデルごとにサーバーを終了してから次を起動し、ポート競合と残留GPUプロセスを確認する。
3. 同じ画像へ異なる質問を連続送信する小ベンチマークを実行し、画像をA→B→Aと切り替えたときの結果・速度も確認する。これにより、速くなる一方で古い画像の状態を再利用してしまう事故を検出する。
4. 全件分類を両版で走らせ、軸別・キャラ別の出力差、推論失敗、画像当たりリクエスト数、処理時間を比較する。判定が変化する場合は個別例を調査し、改善効果だけを記事に載せない。
5. 上流issueの状態を公開直前に再確認。既に修正済みであれば既知修正との重複を避け、パッチの説明を更新する。公開手順にはビルド方法に加え、未改造環境へ戻す方法を入れる。

**退出条件:** コミット・差分・ビルド・実行条件から別PCで再現可能。未改造/改造で画像混線なし。結果の不一致がある場合は原因と採用可否を明記。

### Phase 5: レポート・公開準備

1. 集計スクリプトで同じmanifestを採点し、キャラのTP/FP/FN、複数キャラ画像での完全一致、一般軸の一致率、ルール証拠の正確さ、矛盾例の見え方、失敗率、latencyの中央値・p90を報告する。Nが小さいため画像別結果を主資料として添える。
2. READMEにはクイックスタート、モデル/サーバー設定、専用データセットの生成経緯、判定構造、スコアの意味、Qwen/Gemmaの用途範囲、キャッシュ改造の任意手順、既知の失敗を載せる。
3. note記事はJevとDiffusionGemma報告からの着想、分類器の構造、新規データセット、同条件比較、SFWでのGemmaの位置付け、Qwenの画像再エンコードと改造による影響、失敗例の順に書く。出典URL、ライセンス、計測したコミットを付ける。
4. 公開前に画像・コミット履歴・設定ファイルを点検し、非公開画像、元アプリのDB、APIキー、個人パス、LoRA重み、権利未確認素材の混入がないことを確認する。

**退出条件:** 別環境からREADME通りに再現、公開用レポートが固定タグとコミットを参照、記事の数字とCSVが一致。リポジトリ公開とnote投稿はこの後に実施。

## 5. 評価規則

- **分母:** 該当splitの全ケース。通信失敗や回答形式不正は件数を出し、成功ケースだけを母数にした精度を主要結果にしない。画像判定の主集計は元画像(派生ケースを除く)を分母とし、水増しを防ぐ。派生ケースを含む全ケース分母の値も併記する。メタデータの集計は全ケースを分母とする。
- **一般軸:** 単一軸はcase一致、複数軸はラベル集合のmicro/macro precision・recall・F1を計算する。`other`の扱いを固定する。
- **キャラクター:** 各人物のTP/FP/FNに加え、画像内の全キャラ集合が完全一致する比率を報告。似たキャラ群、二人絵群の例別表を併記。
- **メタデータ:** LoRA指定検出をmanifest内の生成情報・改変履歴と照合。画像上の正解は別評価にし、指定だけでキャラ同定のTPを稼がない。
- **速度:** 下記「時間測定プロトコル」で定義した1画像処理時間（平均・p50・p90・件数）、内部の軸別時間、APIリクエスト数、初回ロード時間を区別。VRAM/GPUオフロード、画像サイズを必ず添える。
- **安定性:** Qwen/Gemmaの回答ラベル欠損、APIエラー、thinkingによる形式崩れ、改造版の画像混線を別々に数える。
- **通常JSONとの比較:** 同じ画像、同じモデル重み・ランタイム・分類体系・メタデータ条件を使う。入力/出力トークン数、1回目の応答時間、再試行込み総時間、形式不正率、同一caseでの正誤を出す。方式差の比較は分類のみJSONを主表とし、自由文要約付きは別表にする。順序効果を避けるため条件の実行順を入れ替え、ウォームアップを除外する。
- **再現性:** `run.json` に実行日、Git commit、dataset/taxonomyハッシュ、モデルGGUF/mmproj SHA256、サーバーcommit、パッチ有無、設定、OS/GPUを保存。
- **しきい値:** 探索用画像群で決め、最終評価群を見てから変えない。変更時は新しい実験IDを振り、旧結果を残す。小規模データのため統計的な一般化を過大評価しない。

### 5.1 時間測定プロトコル

1. **主指標 `classification_wall_ms`:** 評価器側で `time.perf_counter_ns()` を使用し、1件について分類関数の呼び出し直前（画像ファイルの読み込み・リサイズ・メタデータ抽出・ルール照合より前）から、最終分類結果の受け取り直後（出力検証、再試行、フォールバック、タグの検証・統合を含む）までを測る。軸ごと単独、束ね質問、通常JSON分類で同一の開始・終了境界を使う。結果ファイルへの書き込みと集計は含めない。計時内で例外が発生した場合も経過時間・エラー・正誤を記録する。測定境界外で事前計算したメタデータや画像バイト列を一方式だけに渡さない。
2. **補助指標:** 初回API応答時間、再試行込みのAPI呼び出し別時間、1件あたりAPI回数、入力・出力トークン数、前処理時間、軸別時間、サーバー側で取得できるvision/prefill/decode時間を別欄に保存する。取得できない値は `null` とし、サーバー内部の時間をクライアント側の経過時間と同一視しない。全件の実行経過時間と件/秒も別に報告する。
3. **既存実装との対応:** 元アプリの `classify_fast()` の `decisions._timing.total` は関数内で画像準備の直前に始まり、タグの検証・重複除去より前に確定する。軸別 `_timing` と `_request_count` は参考内訳として記録するが、方式間の主指標には流用しない。既存の8枚比較は探索結果としてのみ引用し、専用データセットで再計測する。
4. **測定条件:** モデルロードと事前に定めたウォームアップを本測定から除外し、その回数・内容を記録する。原則1クライアント、1件ずつの逐次実行で測定し、並列処理のスループットは別実験とする。同じ画像順で条件を交互に実行して順序効果を抑え、画像の再利用によるキャッシュ状態（同一画像の連続送信、A→B→Aなど）を明記する。画像解像度、量子化、GPUオフロード、コンテキスト、サーバー設定、パッチ有無を `run.json` に固定する。
5. **報告:** 成功・失敗を含む全件の時間を一次記録し、成功件のみの分位値を併記する際は分母を明記する。24元画像の派生ケースがある場合は元画像IDで対応付け、ケース別の正誤・時間・API回数を公開する。キャッシュ改造の効果は同一llama.cppコミットの未改造版と改造版について同じ測定境界で比較し、LM Studioとllama-serverの差をパッチ効果に含めない。

参考として、`jev_local` の `tools/benchmark_jglue.py` は合成ウォームアップ後にクライアント側の `time.perf_counter()` でAPI送信前から応答の検証後まで測り、標準設定では4件を並列実行する。ここでのAPI往復時間と本計画の画像1件の分類完了時間は測定単位が異なるため、絶対値の直接比較には用いない。出典: https://github.com/Argos1111/jev_local/blob/main/tools/benchmark_jglue.py

## 7. 判定ポイント

- **標準Qwenでfast modeが成立しない場合:** 対応するモデル/ランタイム/設定の組合せを確かめる。成立しなかった設定を記録し、別モデルで出した結果を通常版9Bの結果と偽らない。
- **Gemmaで精度が十分だが一部軸が弱い場合:** SFWの一般分類に範囲を限定する。キャラ同定の弱さも画像例で報告する。
- **キャッシュ改造で判定不一致・画像混線が出る場合:** パッチは公開手順の推奨から外し、再現実験と限界として掲載する。
- **データセットが予定枚数に達しない場合:** 不足の理由と実数を公表し、ケースを足す際は新dataset版として再実験する。
- **X原投稿の短縮URLが特定できない場合:** 確認済みのGoogle Gemma投稿とvLLM PR #57250を引用する。開発者のX原投稿URLは推測しない。

## 8. 記事で検証する主張と必要な証拠

| 主張候補 | 必要な実証 |
|---|---|
| 通常JSONより選択式がキャラ判定に向く | 同一モデル・同一セットのE1対E1-J、E2対E2-J。速度、精度、形式不正、再試行込み時間を両方示す |
| メタデータと容姿を分けると矛盾が分かる | 対照群E8のケース別表示と正解の由来。E8は追加課題化(2026-09-28)のため初版の記事では扱わない |
| GemmaはSFWの実演に有用 | E2の一般軸・キャラ軸・遅延・失敗例を分けて提示 |
| Qwenでは画像キャッシュ改造が効く | E3/E4/E5、同commit・同GGUF・同mmprojで速度と出力を比較 |
| 複数キャラを拾える | 二人絵の全ケース結果とTP/FP/FN |

上記のどれも結果によっては成立しない。記事の見出しと数値は評価終了後に確定し、過去の無検閲版の8/8等を標準Qwenや今回の専用セットの成果として表示しない。

## 9. 着手時の具体的な最初の一手

1. 自作Alisaと比較用の別キャラについて、公開してよい容姿基準と画像生成手段を確定する。
2. 24元画像の生成表と正解付与規則を作り、モデルの結果を見る前に版を固定する。
3. LM Studioで通常版Qwen/Gemmaのvision + logprobsのprobeを先に実行し、使うGGUFを確定する。
4. その後、最小分類コアと評価系を実装する。llama.cppの改造評価は同一コミットの未改造版が動いた後に行う。
