# DiffusionGemma の追加検証(issue #12)

issue #4 の全件評価([`README.md`](README.md))の続き。VRAM と KV キャッシュ、並列実行、画像キャッシュの持ち、画像トークン数、迷ったときだけ読み増す方式(adaptive)を測った。**各条件は1回ずつの測定**(小標本)で、強い結論は書かない。スコアは候補内で割り直した**相対スコア**(正答確率ではない)。数値の出典は、issue #12 のコメントと、このフォルダの `adaptive/` `mst/` の `run.json` / `summary.md`(個人パス除去済み)、測定時の vLLM ログ。

## 1. 目的

- 本番設定で使う `--gpu-memory-utilization` と画像トークン数(`max_soft_tokens`)を決める。
- 並列実行が効くか、画像のプレフィックスキャッシュが何を助けるかを確かめる。
- outfit の過剰な yes と seed による失敗を、迷った質問だけ読み増すことで減らせるかを試す。

## 2. 条件

| 項目 | 内容 |
|---|---|
| ランタイム・GPU | vLLM `ab5266769` + `vision_prefix_lm` パッチ、RTX 3090 単独、`--max-num-seqs 2`、canvas 256 |
| 判定サーバー | 本リポジトリの `dgemma-server`。本番設定(keyed / `Y: yes`・`N: no` / default 指示 / 名寄せ / 16問1回 / samples 1) |
| データ | 元画像31枚。待ち時間はクライアント側の壁時計 |
| 既定の比較 | `--gpu-memory-utilization 0.88`、画像トークン 140(adaptive の比較)、seed 0 |
| 画像トークン | vLLM はリクエストごとの `mm_processor_kwargs` を既定で拒否する(`--trust-request-mm-kwargs` が必要)ため、サーバー起動時の `--mm-processor-kwargs '{"max_soft_tokens": N}'` で指定し、値ごとに vLLM を起動し直した |

## 3. 結果

### 3.1 `--gpu-memory-utilization` と KV キャッシュ

| 値 | KV キャッシュ | 3090 の空き | キャッシュに無い画像1枚の時間 |
|---|---|---|---|
| 0.80(#13 の評価) | 2.9 GiB / 13,772 トークン | 3.85 GB | 平均 466 ms |
| 0.94 | 6.26 GiB / 29,730 トークン | 0.75 GB | **31枚で平均 3,734 ms(大幅に遅い)** |
| 0.88 | 22,891 トークン | 2.16 GB | 31枚で平均 500 ms |

0.94 ではキャッシュに無い画像の処理が約8倍遅くなった。キャッシュが当たった読み出しは 0.18 秒で、遅くなっていない。VRAM の余裕がなくなり、画像処理などの作業領域が足りなくなったためと考えられる(推測)。0.88 は 0.80 と同程度の速さのまま、KV キャッシュが約1.7倍(画像約17枚分)になった。

0.88 の VRAM 内訳(vLLM のログ):

| 項目 | 量 |
|---|---|
| 重み | 15.13 GiB |
| torch 外の使用(non-torch) | 0.53 GiB |
| ピーク時の activation | 0.64 GiB |
| CUDA graph | 0.47 GiB(2回目のキャプチャで 0.10 GiB) |
| KV キャッシュ | 4.82 GiB = 22,891 トークン |
| 確保量 | 24.0 GiB のうち 21.12 GiB |
| nvidia-smi の使用量 | 22,168 MiB、空き約 2.1 GiB |

### 3.2 並列実行

キャッシュに無い画像(0.88、JPEG の画質を変えて毎回まだ処理していない画像にした)。

| 同時に投げた本数 | 全体の時間 | 枚/秒 | 1枚の待ち時間 mean / p50 / max | 失敗した質問 |
|---|---|---|---|---|
| 1 | 15.5 s | 2.00 | 500 / 480 / 556 ms | 0 |
| 2 | 15.0 s | 2.06 | 954 / 969 / 1224 ms | 0 |
| 4 | 12.3 s | 2.53 | 1527 / 1561 / 1829 ms | 1 |

2本同時でもスループットはほぼ変わらない(GPU がすでに埋まっている)。4本では約1.27倍だが、vLLM が同時に処理するのは2本までなので残りは順番待ちになり、1枚あたりの待ち時間が延びる。

再読み出し(10枚、画像トークン 140、0.88、JPEG 品質 95 でキャッシュなし。2026-10-03):

| | mean / p50 |
|---|---|
| 1回目(画像処理込み) | 461 / 385 ms |
| 再読み出し2回を逐次 | 269 / 268 ms(1回あたり 135 ms) |
| 再読み出し2回を同時 | 246 / 247 ms |

再読み出しの `cached_tokens` は 1152〜1184。再読み出しは、逐次でも同時でも大差ない。

### 3.3 キャッシュの持ち(0.88)

| | 枚/秒 | 1枚の待ち時間 mean / p50 / max | 画像までキャッシュが当たった件数 |
|---|---|---|---|
| 1周目: まだ処理していない15枚、seed 0 | 1.94 | 514 / 492 / 805 ms | 0/15 |
| 2周目: 同じ15枚、seed 1 | 7.13 | 140 / 139 / 155 ms | 15/15(cached_tokens 1312 / prompt 1313〜1325) |

キャッシュに収まる枚数なら、時間をおいても seed を変えても画像の処理は使い回され、約3.7倍速かった。#13 で見た「キャッシュが当たっているのに 860 ms」は今回は再現しなかった。

### 3.5 迷ったときだけ読み増す(adaptive)

仕組み: 1回目で、各質問の相対スコアの正規化エントロピー(0〜1)を出す。しきい値以上の質問(と失敗した質問)を対象にして、seed をずらして1回ずつ読み増す。読むたびに対象の質問の累積平均のエントロピーを計算し、全部しきい値を下回ったら打ち切る(上限3回)。差し替えるのは対象の質問だけ。CLI は [`../../cli.md`](../../cli.md) の `--dgemma-adaptive-threshold` / `--dgemma-adaptive-max`。

条件: 本番設定、画像トークン 140、0.88、seed 0。条件ごとに vLLM を起動し直した(キャッシュは空)。元画像31件、各条件1回。記録は [`adaptive/`](adaptive/)。

| 条件 | 単一5軸(/155) | キャラ完全一致 | 服装完全一致 | キャラ TP/FP/FN | 服装 TP/FP/FN | 失敗した軸 | 読み増しした画像 | 平均読み出し回数 | 迷ったまま(質問数) | 時間 mean / p50 ms | 読み増しした画像の時間 mean |
|---|---|---|---|---|---|---|---|---|---|---|---|
| A 1回読み | 143 | 27/31 | 19/31 | 24/1/3 | 25/15/0 | 1 | 0/31 | 1.00 | 0 | 458 / 423 | - |
| B 常に3回 | 143 | 26/31 | 23/31 | 23/1/4 | 26/9/0 | 0 | - | 3.00 | - | 705 / 673 | - |
| C 迷ったら(0.1) | 143 | 25/31 | 22/31 | 22/1/5 | 26/10/0 | 0 | 21/31 | 2.32 | 31 | 628 / 685 | 694 |
| D 迷ったら(0.43) | 143 | 26/31 | 22/31 | 23/1/4 | 26/11/0 | 0 | 16/31 | 1.94 | 13 | 566 / 558 | 661 |
| E 迷ったら(0.87) | 143 | 26/31 | 22/31 | 23/1/4 | 26/12/0 | 0 | 6/31 | 1.35 | 3 | 509 / 450 | 685 |

読み増しのきっかけになった質問は、どのしきい値でも `outfit_other` と `character_other_original` が大半(C: 16件・11件、D: 12件・6件、E: 4件・2件)。「迷ったまま」で上限に達した質問も、この「その他」の選択肢が中心。

- 単一5軸はどの条件でも 143 のまま。
- 服装は、読み増しで 19 → 22〜23/31。余計に付ける件数(FP)が 15 → 9〜12 に減った。
- キャラは 27 → 25〜26/31(見落とし FN が 1〜2件増えた)。seed による揺れと同程度の差。
- 失敗した軸は 1 → 0。
- E(0.87)は読み増すのが 6/31 枚だけで、平均の時間は +51 ms(+11%)。服装の改善と失敗0は C・D と同じで、常に3回読む B より約200 ms 速い。

### 3.6 複数ステップ(steps)

`--dgemma-steps N` は、スロット以外の全位置を固定して N ステップ回し、最終ステップの分布を読む(エンジンが収束と判定すれば N 回に満たず止まることがある)。出典: issue #12 のコメント(オーケストレータの測定)。生の記録は [`steps/`](steps/)。

| 条件 | 単一5軸(/155) | キャラ完全一致 | 服装完全一致 | キャラ TP/FP/FN | 服装 TP/FP/FN | 失敗した軸 | 時間 mean / p50 ms |
|---|---|---|---|---|---|---|---|
| steps 1 | 143 | 27/31 | 21/31 | 24/1/3 | 24/11/0 | 2 | 465 / 437 |
| steps 2 | 143 | 26/31 | 23/31 | 23/1/4 | 26/8/0 | 0 | 544 / 523 |
| steps 4 | 143 | 25/31 | 23/31 | 22/1/5 | 26/8/0 | 0 | 595 / 567 |
| steps 8 | 144 | 24/31 | 23/31 | 21/1/6 | 25/7/1 | 0 | 752 / 720 |

sharpness(答えた質問の正規化エントロピー): steps 1 は平均 0.0361・中央値 0.0001、0.1 以上 31 件、0.43 以上 15 件(n=480)。steps 2 は 0.0197 / 0.0005、24、5(n=496)。steps 4 は 0.0190 / 0.0005、19、5(n=496)。steps 8 は 0.0147 / 0.0003、19、2(n=496)。

- 服装は steps 2 で良くなり、その先は横ばい。キャラはステップが増えるほど下がる(見落とし FN が 3 → 6)。
- 迷いが隠れる(分布が鋭くなる)ので、エントロピーで再読み出しを決める adaptive とは相性が悪い。
- vLLM は指定のステップ数に満たず止まることがあるが、実際のステップ数は記録していない。
- 各条件1回の測定。steps 1 と adaptive の A(同じ設定)で、服装が 2 件、失敗が 1 件違った(実行ごとの揺れ)。
- 条件は adaptive の実行と同じ(MST 140、0.88、seed 0、条件ごとに vLLM を再起動、`vision_prefix_lm` パッチ適用)。

## 4. 結論

- **推奨サーバー設定: `--gpu-memory-utilization 0.88`、`max_soft_tokens 140` をサーバー全体で指定**(`GPU_MEM_UTIL=0.88 MST=140 bash scripts/dgemma/serve_vllm.sh`)。0.94 は余裕が足りず遅くなる。70 は精度と失敗が悪化する。
- **推奨は steps 1 + adaptive(しきい値 0.87、上限 3)に、迷いの印(`uncertain`)を付ける使い方**(`--dgemma-adaptive-threshold 0.87 --dgemma-adaptive-max 3`)。上限まで読んでも迷いが残った質問は、答えに `uncertain: true` と `entropy` が付く。steps は選択肢として残す(既定は 1)。複数ステップは服装を改善したが、キャラが下がり、迷いが隠れる(3.6)。
- 並列は、この構成(`--max-num-seqs 2`)ではほとんど効かない。
- 画像キャッシュは、同じ画像に何度も質問するときに効く(再読み出し 135 ms 前後、2周目は約3.7倍速)。
- adaptive をしきい値 0.87・上限 3 で使うと、この1回の測定では、服装完全一致が 19 → 22/31、失敗した軸が 1 → 0 になり、平均時間は +51 ms だった。キャラは 27 → 26/31 で seed による揺れの範囲。きっかけは主に「その他」系の選択肢。既定にはせず、オプションとして用意する。

## 5. 限界

- 各条件は1回(画像トークンは seed 2つ)の測定。差は 1〜数件で、強い結論は書かない。
- adaptive のしきい値は、同じ31枚の過去の結果を見て決めた。**探索的な結果**で、別の画像での検証はしていない。
- GPU 計算の非決定性により、同条件の再測でも失敗数や完全一致がずれる。
- リクエスト単位の `mm_processor_kwargs` は vLLM が既定で拒否するため、画像トークンは起動時の指定のみで比べた。
- 0.94 が遅くなった理由は推測。並列・キャッシュの測定は、各条件1回。

## 6. 「その他」の質問文(`--dgemma-catchall-style`)

出典: issue #12 のコメント(2026-10-03「seed による失敗の原因調べ」「「その他」の質問文の言い換え」「その2」。オーケストレータの測定)。分類体系の中身は変えず、`catch_all` の選択肢の質問文の組み立て方だけを変えた。生の記録は [`catchall/`](catchall/)(`<書き方>_s<seed>/`)。**`list` の実行は、のちに削除したコード(ブランチ上の `ce91e13`)で行った**(結果だけを失敗した試みとして残す。現在の CLI には `default` と `criteria` だけがある)。

### 6.1 seed による失敗の原因調べ

- 失敗(`label_mass_low`)は、ほぼすべて「その他」の質問で起きていた。`dgemma_mst280_seed1` は9件中 `outfit_other` 8件・`character_other_original` 1件、`dgemma_own_seed1` は8件中7件・1件、`dgemma_own_seed2` は5件すべて `outfit_other`、`dgemma_steps_1` は2件とも `outfit_other`。
- 特殊トークンの混入は否定的(tokenizer の added tokens は24個で、どの答えの位置にも入っていなかった)。
- `outfit_other` の位置では、` own`、`-`、意味の通らないトークンに確率が流れる(`N`/`Y` 以外を書こうとしている)。
- まったく同じキャンバスでも、読むたびにラベル質量が大きく揺れる(例: S04(JPEG 画質 96)は 0.571 / 0.536 / 0.734 / 0.364、C01(画質 90)は 0.097 → 0.697)。キャッシュの有無だけでは説明できない。
- 暫定の結論: 失敗の主因は seed のノイズそのものではなく、**「その他」の質問はもともとラベル以外に確率が流れやすく、それがエンジン側の計算の非決定性で 0.5 の境目をまたぐ**こと。非決定性の出どころ(非同期スケジューリング、CUDA graph、バッチの組み方など)は未調査。

### 6.2 言い換えた質問文

- `list`: 服装 `Apart from sailor school uniform, school uniform, office wear, swimsuit, maid outfit, shrine maiden outfit and nun's habit, is there at least one other clothing (clothing whose type is recognizable but fits none of the above) in the image?`、キャラ `Apart from Alisa and Second original character, is there at least one other character (any person or humanoid character who is neither Alisa nor the second original character) in the image?`
- `criteria`: 服装 `Does the image show clothing whose type is recognizable but fits none of these: sailor school uniform, school uniform, office wear, swimsuit, maid outfit, shrine maiden outfit and nun's habit?`、キャラ `Does the image show any person or humanoid character who is neither Alisa nor the second original character?`

条件: 本番設定(keyed / `Y: yes`・`N: no` / default 指示 / 名寄せ / 16問1回 / 1ステップ / samples 1、読み増しなし)。画像トークン 140、0.88。条件ごとに vLLM を起動し直した(キャッシュは空)。元画像31件、各条件1回の測定。

### 6.4 結論

- **推奨は `--dgemma-catchall-style criteria`**(既定は従来の `default` のまま)。
- `list` の「Apart from」は、他の選択肢の存在を前提にする書き方が害になった。失敗した試みとして結果だけを残し、コードは削除した。
- 各条件1回(seed 2つ)の測定で、31枚での差は数件。強い結論は書かない。
