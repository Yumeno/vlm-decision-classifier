# DiffusionGemma(issue #4)の結果

拡散言語モデル DiffusionGemma を vLLM で動かし、**画像1枚・全質問を1回の読み出しで**選択式分類できるかを、同じ元画像31枚・taxonomy v0.4.1 で通常JSON(`dgemma_json`)と対応比較した記録。各設定は**1回ずつの測定**(小標本)で、強い結論は書かない。スコアは候補内で割り直した**相対スコア**(正答確率ではない)。

数値の出典は、全件評価の `run.json` / `summary.md`(このフォルダの `seed0/` `seed1/` `seed2/` `standard/`)と、実験中の probe メモ(リポジトリ管理外)。probe の表は同じ画像・同じ条件(下記)で各1回測ったもの。

## 1. 目的

拡散LMは1回の順伝播で出力キャンバス全体の分布が出る。そこで、質問ごとの回答スロットをキャンバスに並べ、**画像を1回送り、全質問(16問)を1回の読み出しで**聞く。自己回帰VLMが質問ごとに1リクエストを要するのに対し、読み出し回数と時間をどこまで減らせるかを見る。

## 2. 条件

| 項目 | 内容 |

| ランタイム | vLLM `ab5266769` + openjev の `vision_prefix_lm` パッチ(画像トークンの双方向化。パッチ本体はリポジトリに含めない) |

| KV キャッシュ(vLLM ログ) | 0.80 のとき 2.9 GiB / 13,772 tokens。評価後に 0.94 へ上げた分は 6.26 GiB / 29,730 tokens(本評価には未使用) |

## 3. 経緯(うまくいかなかった設定も含む)

1. **vLLM の example 構造化サーバー**(16問を1リクエスト、samples auto): 単一5軸の正答は 140/155 だが、キャラ完全一致 7/31・服装 12/31 と、yes/no を含む10問超で崩れた(`results/dgemma_standard` = `standard/summary.md`、旧コード `5ebf329`。参考のみ)。
2. **自前サーバー**: 回答欄の書式が主因と見て、`<質問id>: <ラベル>`(keyed)と `Q<n>: <ラベル>`(numbered)を比べた。numbered は全滅(キャラ・服装とも 0/31)、keyed はキャラ 25/31。
3. **1回に読む質問数**を分けると(8問×2、4問×4、1問×16)、キャラ・単一軸は上がる設定もあるが、時間が延びる(下記 4.1、4.3)。1問ずつは却って悪化。
4. **名寄せ**: 失敗(`label_mass_low`)の原因は、スロットに記号でなく選択肢名の先頭トークン(` anime` 0.915 / ` A` 0.073 など)を書こうとしていたこと。別表記のトークンの確率を選択肢に合算する名寄せを入れ、16問1回で単一5軸 128→142/155、失敗 19→4(同一書式の別ビルドでの比較。表は 4.1・4.2)。
5. **指示の強化**(`strict` / `strict_sys`)と書式(`slash` / `lines` / `letters` / 質問順): 失敗や服装の誤検出は設定で動くが、一貫して良くなる設定はなかった(4.2)。
6. **yes/no を `Y: yes` / `N: no`**(作者案): 失敗(`label_mass_low`)が 0 になり、label_mass の中央値が 0.996〜0.998 に上がった(4.2)。これを最終設定にした。

## 5. 結論

最終設定(keyed / `Y: yes`・`N: no` / default 指示 / 名寄せ / 16問1回読み / samples 1)では、**1枚あたり読み出し1回・平均約 466〜500 ms** で、通常JSON(平均 1186 ms)の約0.4倍の時間になった。精度は、単一5軸は通常JSON以上、キャラは同等、服装は通常JSONのほうが上(各1回の測定、元画像31件)。

- 単一5軸: choice 142(seed1・2 は 143・142)、json 136(/155)。
- キャラ完全一致: choice 28/31(seed1・2 は 28・27)、json 28/31。
- 服装完全一致: choice 18〜19/31、json 23/31。**服装は json が上**。choice は outfit の yes/no で school_uniform と other を多く「yes」にする偏り(誤検出)があり、再現率は高く適合率が低い。実用時はメタタグ併用の想定(作者判断。分類体系は変えない)。
- 時間: choice の mean 466 ms に対し json 1186 ms(同一 run 内の対応比較。p50 は 494 / 951 ms)。json は形式不正 2/31(再試行で平均 1.19 リクエスト)。choice の失敗は outfit 軸 1 件(seed0)。
- seed を変えた揺れ: 単一5軸 ±1、キャラ ±1、服装 ±1、軸の失敗数は outfit 1 / 6 / 5 と大きく振れた(下記)。

## 6. 限界と未解決

- 小標本(元画像31枚。派生は同一画像の束ね)で、各設定は1回の測定。差は 1〜2 件の範囲に収まるものが多く、強い結論は書かない。
- GPU 計算の非決定性: 同条件の再測で失敗数や完全一致が 1〜2 件ずれる(原因は推測)。
- **画像のプレフィックスキャッシュは KV 容量に制約される**: 0.80 では KV が 13,772 tokens で、1画像のプロンプトが約 1,250〜1,310 tokens(cached_tokens の値)なので、保持できるのは画像約10枚分。seed0 の時間は画像キャッシュ空からの測定で、seed1・2 の時間はキャッシュの追い出しと整合するが、下記の例外もあり断定しない。0.94 で KV を 29,730 tokens に増やした実行は報告していない(未測定)。
- seed1/2 でキャッシュ済みのはずなのに下がらない時間(例: A02 が cached_tokens 1312 なのに 860ms)は原因未調査。
- seed1・2 では outfit 軸の失敗が 6 と 5(seed0 は 1)。原因は未解析(失敗した質問は seed1 で 8 件、seed2 で 5 件、いずれも `dgemma_format_error`。各 `summary.md`)。
- 並列実行時のスループットは未測定(`--max-num-seqs 2` で動かした逐次のみ)。
- example サーバーのエントロピーの定義は未確認。auto で読み増しになる画像の数は本表から直接は言えない。
- `taxonomy/default.yaml` は意図して変えていない。キャラの説明文を特徴の列挙に縮める案は**将来やる可能性があり**、やるなら分類体系の新しい版(例 v0.5.0)の別実験にして旧結果を残す。
- 追跡する issue: [#11](https://github.com/Yumeno/vlm-decision-classifier/issues/11)(llama-server 側の名寄せ・Y/N 書式)、[#12](https://github.com/Yumeno/vlm-decision-classifier/issues/12)(DiffusionGemma の追加検証: 並列、キャッシュ、outfit の yes バイアス、seed による失敗、エントロピーの再確認)。
- vLLM の起動スクリプトは `scripts/dgemma/`(報告した実行は gpu-memory-utilization 0.80。0.94 は #12 用)。
- `standard/` は旧コードと example サーバーによる参考実行で、最終設定との比較には使わない。
