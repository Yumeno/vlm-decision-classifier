# 実験レポート — ローカルVLM選択式画像分類デモ

## 1. 概要

本デモは、Jev的な選択式判定(回答ラベルの `logprobs` から候補間の相対スコアを読む方式)を、マルチモーダル入力・任意のローカルVLMに適用したときの挙動を確かめる技術検証である。分類の精度そのものを追い込むことや、メタデータ補助による精度向上は目的にしていない。

専用に新規生成した画像データセット(元画像31枚、メタデータ除去コピー4件の計35ケース)を使い、通常版Qwen3.5 9B GGUFとGemma 4 12B GGUFの2モデルで、選択式方式(`choice`)と通常のJSON生成方式(`json`)を同一条件で対応比較した。Qwenについては、`taxonomy` の `none` 選択肢の文言修正前後(0.4.0→0.4.1)の再評価と、llama.cppの画像キャッシュ改造の有無(未改造/改造)による速度比較も行った。

その後、改造版llama-serverで「確認(yes/no)のオン・オフ」「軸の並列送信」「画像の準備(ホットロード)」を変えたE9系、および全軸を1リクエストで答えさせる束ね質問と送信画像(形式・長辺)を変えたE7系を、同じデータセットで追加した。

**記事の本表は、これらの試行錯誤のあとに1つのコミット・同じ条件で取り直した「最終の取り直し」(F1〜F3)を、`--prime` の不公平(6章)を直したコード(PR #20)で「準備なし・準備あり」の2条件に測り直した結果(1.2)である。** さらに小型モデル(Qwen3.5 4B/2B/0.8B、Gemma 4 E4B/E2B)も同じ手順で測り直した(S1〜S9、1.3)。E1〜E5・E9・E7の結果(第4章)は、そこへ至る経緯(試行錯誤)として残している。旧・最終の取り直し(JSON だけ準備が効いていなかった測定。精度は同じだが時間比較は不公平)は1.2の末尾に残した。

以下の数値は各実験フォルダの `summary.md`・`cases.csv`・`run.json`(E5は `vanilla.json`/`patched.json`)、測り直し(F1〜F3・S1〜S9)は `doc/experiments/reprime/summary.md`(旧測定は `doc/experiments/final/summary.md`・`doc/experiments/small/summary.md`)を一次資料として転記したものである。元画像N=31件と小標本のため、1〜2件の差は誤差の範囲として扱い、強い結論は書かない。精度の数値は「選択式という方式が実際にどう振る舞うか」を見るための材料であり、改善余地の列挙が目的ではない。

### 1.1 議論の大前提(画像を扱うことによる必須のオーバーヘッド)

既存のVLMをJevのように使うと、画像を扱うための処理が必ず乗る。テキストだけを扱うオリジナルのJevやJev亜種ほどは速く処理を終えられない、という構造上の制約がある。ただしJevは同じ環境で測っていない。以下は速度の比較ではなく、構造の話である。

残るオーバーヘッドは2種類ある。

- **画像を最初に読み込む費用(1枚につき1回)**: 画像のエンコード。E7の実測で、長辺768で0.55秒、長辺1024で0.80〜0.84秒(下記4.8)。キャッシュでは消せないが、長辺で減らせる。
- **リクエストごとの費用**: キャッシュが効いても毎回残る。OpenAI互換APIでは毎回画像を送り直して照合する(JPEGにすると1リクエストあたり約40ミリ秒減った)。また、キャッシュからの状態復元にも時間がかかる(Qwen3.5 9Bのサーバーログで、14トークンの処理でも約130ミリ秒。この数値は作業記録 `doc/worklog.md` の観察で、本レポートの一次資料には含まれない)。キャッシュからの復元の重さは、モデルの構造(QwenのSSM、GemmaのSWA)に依存する。当初は「Qwen3.5の混合型(SSM)による部分が大きい」と推測したが、最終の取り直し(1.2)でGemma(SWA)のほうが1リクエストの固定費が大きかった(約350ミリ秒 vs 約130ミリ秒。サーバーログの観察で `doc/worklog.md` に記録。SWAのチェックポイント復元とみられるが未検証の見立て)ため、この推測は外れた。大きさはモデルとサーバーに依存する。

この前提から、以下の順で結果を読む。

1. リクエストごとの費用が回数分積み重なるので、1軸ずつ(1画像あたり7〜11回)は通常JSONより遅くなる(1.2。改造版で JSON の1.14〜1.60倍)。なお4.6のE9c・4.7のE7cでは「JSONと同程度」に見えたが、それらは JSON だけ準備が効いていない不公平な測定だった(6章)。
2. リクエストを1回に束ねると、通常JSONより2〜3割短くなる(1.2。全12条件で14〜33%短縮)。当初の「約2倍速」は、JSONにだけ画像の読み込みが含まれていた不公平な測定による見かけの差だった(6章)。
3. 束ねると自己回帰なので、後ろの軸は前の軸の答えを前提にした条件付きになる(拡散型のモデルなら避けられる性質)。ただしこのデータでは精度低下は目立たなかった(4.7)。
4. 画像の読み込み費用は、送信画像の長辺と形式で減らせる(4.8)。

**観察**(`reprime/summary.md`)
- 1軸ずつの選択式は、小さいモデルでも単一選択の精度がほとんど落ちない(0.8Bでも平均86.5〜87.1%)。JSONは小型ほど形式不正が増えて崩れる(Qwen 2B Q4で失敗9件、単一選択の平均63%)。
- 束ね質問は形式を守れるかに左右される。Qwen 4Bは雛形の番号を付けず記号だけを1行ずつ答え、ほぼ全件が形式不正になった(中身は1軸ずつとほぼ同じ答え)。Y/N欄(16欄)は小型でほぼ崩れる。崩れるモデルは旧測定と同じ(失敗数もS2の束ね(rank)の27→28以外は同じ)。
- 量子化(Q4とQ8)の差は、上がる項目と下がる項目があり、1回の測定でははっきりしない。JSONの失敗数はQ8のほうが同数か少なかった(Qwen 4B 2→2、2B 9→3、0.8B 10→3、Gemma E2B 6→2。いずれもQ4→Q8)。
- 時間(JSONとの比、公平な測定): 1軸ずつ(確認オフ)は0.70〜1.29倍で、小型では遅いとも速いとも言い切れない(JSONの時間には形式不正の失敗ケースも含む)。束ね(rank)は0.34〜0.65倍だが、S1・S2はほぼ全件が形式不正でその時間は失敗した回答の時間。束ね(Y/N)は0.60〜1.17倍。
- 小標本(元画像31件)・1回の測定なので、強い結論にしない。

**結論の整理(作者、2026-09-29。時間の記述は2026-09-30の測り直しに合わせて修正)**
- 傾向として、「束ね質問による処理の高速化」は「モデルが回答の形式をどのくらい守ってくれるか」に成否が依存し、形式を守れない失敗はモデルが小さくなるほど増える(9B・12Bは守れて、束ね(rank)はJSONより2〜3割短い(当初の「約2倍速」は不公平な測定による見かけの差だった)、4Bはほぼ全件が形式不正、Y/N欄のように欄が多いほど先に崩れる)。
- 1軸ずつの選択式は答えが1文字で形式に頼らないので、小型でも崩れにくい。
- 境目ははっきりしない。問いの内容(軸・欄の数)で判断すべき閾値も変わるし、形式を守らせる工夫(行の位置で読む、答えの書き出しを先に書く、文法で縛る等)を重ねれば改善する可能性もある。今回の数字はその傾向の一例。
- 量子化: JSONはQ8で一貫して形式不正が減った。1軸ずつはQ4/Q8でほぼ同じ。束ね質問はQ8で良くなるとは限らない(1回の測定)。

### 4.7 E7: 束ね質問(1リクエストで全軸)

**読み方**:
- 番号付きの束ね質問は、通常JSONより速い(ただし以下の「約2倍」等の比は、JSONにだけ準備が効いていない不公平な測定によるもの。公平な測定では2〜3割の短縮、1.2)。E7cでは判定0.80秒 vs 1.62秒で約2倍、E7b(0.91秒 vs 1.70秒)は約1.9倍、E7d(0.79秒 vs 1.33秒)は約1.7倍(JSONは長辺を下げると縮む)。精度は1軸ずつ・JSONと同等以上に見える(束ね質問の単一軸の一部は+2〜3件)が、元画像31枚で、1〜2件の差は誤差の範囲。
- 束ね質問は後ろの軸が前の答えを前提にする構造だが、「前の答えに引きずられて落ちる」現象は、このデータでは目立たなかった。軸の並べ方を変えた測定はしていないので、順序の影響は切り分けていない(第6章)。
- 1軸ずつは通常JSONと同程度の時間(E7c 1.34秒 vs 1.62秒、E9c 1.67秒 vs 1.71秒)。1リクエストが速くても、回数が積み重なる(前提)。

### 4.8 送信画像の形式と長辺(E7b→E7c→E7d)

- **JPEG(quality 90)**(E7bのPNG→E7cのJPEG、長辺1024どうし): 1軸ずつの判定が1.64秒から1.34秒へ約0.3秒短くなった。リクエストあたりでは約40ミリ秒(0.30秒 / 7リクエスト)で、画像の送り直し(base64)が軽くなった分とみられる。精度は同水準(選択式の単一軸・服装・キャラで、1件以内の差または同じ)。準備は0.84秒から0.80秒。
- **長辺768**(E7cの1024→E7dの768、JPEGどうし): 準備(画像の読み込み)が0.80秒から0.55秒に短くなり、JSONの判定も1.62秒から1.33秒に短くなった。束ね質問の判定はほぼ変わらない(0.80秒 → 0.79秒)。精度は選択式・束ね質問でほぼ同じ(画像の種類の選択式は93.5%から90.3%で1件差)。
- 準備+判定の合計は、E7b(PNG1024)の束ね質問1.76秒 → E7c 1.61秒 → E7d 1.34秒と縮んだ。画像の読み込み費用は、送信画像の長辺と形式で減らせる。ただし長辺を下げると細部の判定に影響しうるが、この小標本の範囲では差は見えなかった。

### 4.9 キャッシュの使われ方で際どい判定が揺れる観察

同じ判定ロジックでも、準備の有無や並列などキャッシュの使われ方によって、際どいケースの予測ラベルが変わった。`cases.csv` の `pred_*` 列を突き合わせた結果(選択式、元画像。全35ケースでは派生に差なし):

- E9aとE4(どちらも確認オン・PNG1024・逐次。準備の有無だけが違う): 5か所が変わった(G02の画像の種類・場面、M02の場面・服装、S03の場面)。
- E9bとE9a: 3か所(A01の服装、G02の画像の種類・場面)。E9b2とE9a: 3か所、E9eとE9a: 4か所。
- E3(未改造)とE4(改造): 全35ケース・全軸で一致(4.5)。E7cとE7b(JPEG/PNG): 1か所(S03の場面)。

キャッシュから復元した状態と、計算し直した状態とでlogprobsがわずかに違い、僅差の候補が入れ替わるとみられる(未検証)。上の変化は、正解から外れる場合と正解になる場合の両方がある(例: E9aとE4の比較では、G02の画像の種類・M02の場面・M02の服装はE4が正解でE9aが不正解、S03の場面はE9aが正解でE4が不正解)。少数のケースの揺れを、条件間の精度差として読まないこと。

### 4.10 複数選択の軸: 順位付けと候補ごとの判定(E7e)

**順位付けの相対スコアは、複数選択に向かない**: 選択式の相対スコアは候補どうしで合計1を取り合う(「どれが一番か」の分布)。2つ写っている画像では確率が分かれ、閾値0.5を超えられるのは片方だけになる。4.6のM01(キャラ)と同じ構造である。次の例は**データセット外**で、作者が正解を判定した1枚(修道服の人物とセーラー服の人物の2人が写っている。服装の正解は `nun` と `sailor_uniform` の両方)。**画像ファイルはリポジトリにない**(公開しない)。評価の分母には含めない。一次資料は `results/trial` のJSON(同じく公開しない)で、数値は `doc/worklog.md` の表の転記。改造版llama-server、JPEG・長辺1024、準備なし、1回ずつの実行。

## 5. 失敗と試行錯誤

- **`none`の選択肢の文言**: E1/E2では「none of the above」という文言が「人物なし」ではなく「上のどれでもない」と読める設計になっており、選択式のcharacterで`other_original`が一度も付かなかった(Qwen)。`none_criteria`の説明文を足す修正(taxonomy 0.4.1)で改善したが、正解ラベルは変えていない。
- **Gemmaの Channel Error(E2のみ)**: yes/no確認2件(G03・G05)がLM Studioサーバー側の`Engine protocol predict request failed: fetch failed`で失敗した。評価器は失敗として分母に残し、E2bでは再発しなかった。
- **JSON形式不正の中身**: 単一選択の軸をリストで返す誤りがあった(E1 の Qwen: O01 の situation、O06 の subject)。
- **`--kv-unified`**: 最初`--kv-unified`なしで起動したところ`n_ctx_slot = 2048`(スロットごとに分割)になり、LM Studio(コンテキスト8192の共有)と条件が変わってしまうため、測定前に停止して付け直した。
- **`-mg`の番号**: `-mg`はCUDAの並びで指定するが、`nvidia-smi`の番号とは逆順だった(この環境ではCUDA0 = RTX 3090)。`llama-server --list-devices`で確認して対応した。
- **スロット再利用**: 改造版は`-np 4`のスロットが複数あるため、画像を切り替えても別スロットに残った古い画像の状態を再利用できてしまう。E5テスト1の「1軸目=再エンコードあり」という前提は、この構成の改造版には当てはまらないと分かった。E3/E4と同じ条件での実際の挙動として、そのままE5の結果に記録している。
- **E7aの束ね質問の形式(記号だけの空白区切り)**: 途中の軸を飛ばした出力で後ろの答えが1つずつずれ、別の軸の答えとして読まれた。番号付き(`1: A`)に変えて解消した(4.7)。E7aの束ね質問の精度は比較に使っていない。
- **E7eの回答形式(Y/N欄16個)**: 欄が増えたところ、番号の代わりに「A: A」と答えて全軸が形式不正になった。回答の雛形を指示文に示して解消した(4.10)。
- **軸の並列送信(E9b/E9b2/E9e)**: 逐次より遅い、または準備を含めた合計で得にならなかった。1回試して打ち切った(4.6)。
- **E9cの `tool_commit` がdirty**: 並列準備の修正を実行中に別作業で編集していたため。修正は並列の経路だけで、逐次のE9cには影響しない(`run.json` の `dirty=true`のまま記録)。

## 6. 限界

- 元画像31枚の小標本。単一軸の候補には1〜3件しかないものがある(`comic`・`ui`・`pixel_art`・`grayscale`・`line_art`等)。候補別の成績は個別例として読み、強い結論にしない。
- 自作データセット(Anima base v1.0 + 自作LoRA)であり、他のモデル・画風への一般化は確認していない。
- taxonomyは評価セットの生成・正解付与後に0.4.0→0.4.1へ調整している(`none`選択肢の説明文追加)。正解ラベルは変えていないが、評価結果を見てからの文言調整である点は限界として明記する。
- RTX 3090 は Thunderbolt 接続の外付け GPU で、PC 内のスロットに挿した GPU より CPU との転送帯域が狭い。モデルは GPU に常駐しているため判定時間への影響は小さいとみているが、測っていない。画像の送信・モデルの読み込み・準備の時間は、内蔵の GPU で測った場合と異なる可能性がある。
- 処理時間は別プロセスの影響を受けうる。E1/E1-J/E2/E2-Jは、別プロジェクトのパッチ適用版llama-serverがGPUに常駐した状態で測定しており(`run.json`の`concurrent_processes`に記録)、E1b以降の測定(RTX 3090に他プロセスなし)と単純比較できない。
- **`--prime` の不具合(2026-09-29 にデモの動作から判明、PR #20 で修正)**: 修正前の `--prime` 付きの実行(E9/E7/E7e、旧の最終の取り直しF1〜F3、旧の小型S1〜S9)は、選択式のsystem文で準備を送っており、JSON方式の先頭(system文が違う)には一致しなかった。そのためJSONの判定時間には画像の読み込みが含まれ、選択式・束ね質問には含まれなかった。これらの実行での「JSON対選択式/束ね」の時間比較は公平ではない(精度は影響を受けない)。**F1〜F3・S1〜S9は、修正後のコードで準備なし・準備ありの2条件に測り直した(1.2・1.3、`doc/experiments/reprime/`)**。E9/E7/E7eは測り直していない(経緯として残す)。
- E9/E7は同じデータセット(元画像31枚)で、確認・軸の並列・準備・送信画像・モードを変えて何度も測っている。条件間の小さな差(1〜2件、ミリ秒単位の差)を選んで読む余地があり、強い結論にしない。E9/E7は各条件を1回ずつ測っただけで、繰り返しによるばらつきは見ていない(4.9の揺れが示すとおり、キャッシュの使われ方で際どいケースの判定は変わる)。
- 束ね質問(E7)は、軸の並べ方を変えた測定をしていない。自己回帰のため後ろの軸は前の軸の答えを前提にするが、順序の影響は切り分けていない。「精度低下が目立たなかった」は、この並びとこのデータでの観察にとどまる。
- E9/E7はQwen3.5 9Bのみ、改造版llama-server(`-np 4`)のみで測った。Gemma 4 12B・未改造版は最終の取り直し(1.2)で測ったが、キャッシュ復元の重さ・リクエストごとの費用の大きさ(1.1)は、モデルの構造とサーバーに依存する。Gemmaの固定費が大きい原因(SWAのチェックポイント復元という見立て)は検証していない。
- 測り直し(1.2)は**各条件1回**の測定。判定は`temperature=0`で決定的で、旧の最終の取り直し(3回)では判定が3回で完全に一致したが、今回は準備の有無や旧測定とのあいだに数件の判定の違いがあった(1.2)。時間のばらつきは旧測定の3回で標準偏差2〜59ms(実行環境の揺らぎ。リアルタイムOSではないため)で、今回は1回なので数十ms程度の差は区別できない(例: F1 準備ありで長辺768のほうが遅い方式がある)。再現性は、同じデータセット・同じ条件のものであり、他のデータや環境への一般化ではない。
- 小型モデル(1.3、S1〜S9)は繰り返し1回の測定。判定の再現性はF1〜F3の3回で確認したが、時間のばらつきは見ていない。旧のS1〜S3の測定中にE2B Q4のダウンロードが並行していたため、旧測定の時間にわずかな影響がありうる(作業記録。測り直しでは並行作業は記録していない)。モデルの配布元・量子化は `lmstudio-community` のGGUF(mmproj BF16)にそろえたが、モデルごとにサイズ・構造・量子化の組が違うため、サイズだけの効果とは読めない(Qwen3.5とGemma 4は世代・構造が異なる)。
- 束ね質問の形式不正は、モデルが回答の雛形をどう読むかに強く依存し、今回の雛形とプロンプトでの結果にとどまる(1.3)。形式を守らせる工夫は試していない。
- E7eのY/N欄は全候補を並べるので、候補が多い軸では欄が増えて遅くなる(この実験では7から16)。服装の似た候補の誤検出は解消していない。修道服とセーラー服の例(4.10)はデータセット外の1枚で、画像は公開しておらず、評価の分母に含めていない。
- Jevは同じ環境で測っていない。1.1の議論は構造の話で、Jevとの速度比較ではない。
- 確認オフの閾値0.5はE9c/E7以降で1条件のみ。閾値を変えた測定はしていない(相対スコアの合計は1なので、0.5では実質1候補しか採用されない)。
- E9のサーバーログの件数(LRU/一致など)は `doc/worklog.md` の記録で、ログ自体は本リポジトリに含めていない。
- E1〜E5は確認オン・PNG・長辺1024、E7c/E7dはJPEG・確認オフで測っており、既定が変わった後の条件と単純比較できない(2章)。

## 7. 追加課題(未実施)

- **E6**(説明文付きJSON生成との比較): 元プロジェクトでは実施済みだが、優先度は低く初版の完了条件に含めない。
- **E8**(`vision_only` 対 `metadata_assisted`、メタデータ補助の寄与を見る対照実験): 2026-09-28、作者の判断で追加課題とした。本デモの目的は選択式判定の技術検証であり、精度を上げるための補助情報の導入(メタデータ補助)は目的にしていないため。
  - 見込み(作者、2026-09-29): メタデータ(LoRA 名・トリガーワード)を判定に組み合わせれば、メタデータのある画像ではキャラ判定が上がる見込み。メタデータの読み取りは全35ケースで正解だった(4.3)。ただし、この評価セットでは画像だけの束ね質問・Y/N 欄(E7e)がすでにキャラ 31/31 で、上げる余地があるのは1軸ずつ(90.3%)や JSON(87.1%)。メタデータのない画像(外部ツールの生成、メタデータ除去、LoRA なしの似たキャラ)には効かず、LoRA の指定と見た目が食い違う画像(C01・C02)ではメタデータをそのまま答えにすると誤るため、本デモは2つの証拠を分けて並べる設計にしている。
